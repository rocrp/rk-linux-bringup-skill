# 11 人机协作

> 这套方法能跑通，一半靠技术，一半靠分工。
> 核心判断：**边界是"物理 vs 数字"，不是"决策 vs 执行"。**

## 1 分工

| | 人 | agent |
|---|---|---|
| 物理世界 | 断电上电、插卡拔线、按 MaskROM、刷机、量电压、焊接、听声音、看画面 | 无 |
| 数字世界 | 拍板、验收、对外提交 | 查资料、读日志、反编译、写 DTS/脚本、编译、比对、写文档、备料 |
| 责任 | 对外（署名、发言、发布） | 对内（每条结论都要有出处） |

注意两点：

- **决策不是人的专属**：可行性判断、阶段顺序、方案取舍，agent 都可以先出草案；
  人保留否决权。
- **agent 在物理世界是盲的**：它只能通过人的描述、日志和照片感知硬件。
  所以"让人做一个动作"必须写到"手怎么放"。

## 2 八条规则

1. **先三行汇报，再动手。**
   现在在哪 / 我准备做什么 / 需要你做什么。超过 5 分钟的动作之前都要有一次。
2. **大动作先方案。**
   给选项 + 推荐 + 风险，等人一句"按 A 来"。刷机、改启动配置、重建镜像、提 PR、
   动他人机器目录，都算大动作。
3. **结论挂证据，并分清"实测 / 推断 / 未验证"。**
   证据优先级：设备原始输出 > 万用表读数 > 截图 > 上游源码 > 论坛说法。
4. **要人动手时一次只要一件事。**
   "请断电—等 5 秒—上电—告诉我电压"是一个动作；不要一次给五步让人自己排。
5. **物理事实优先于模型。**
   被告知"不是这样"时，先接受、再改假设，不辩护。人也会自我纠错，对事不对人。
6. **长命令后台跑 + 增量播报。**
   >30 s 的命令放后台，报"已完成/总量 + 当前在做什么 + 下一锚点"，禁止攒到最后一次性输出。
7. **文档分层不串。**
   计划 = 冻结的路线；进度 = 一句话 + 每小阶段一行 + 日志索引；日志 = 唯一放细节的地方。
   计划定稿要人确认；定稿后改计划，必须人提出或批准。
8. **收尾三件事后停手。**
   写日志 → 更新进度 → 列"改了哪些文件 + 建议提交说明"，然后停下来。提交由人做。

元规则：**同类纠正出现第二次，就写进项目规则文件**（`templates/project-AGENTS.md`）。
把"记忆"外置成仓库文件，比在对话里反复叮嘱可靠。

## 3 停点

以下情况必须停下来等人，不能自主连续做：

- 任何物理动作：断电/上电、插拔、按 MaskROM、刷机。
- 写目标存储/分区/引导区。
- 改电源使能、复位脚、GPIO 极性（可能伤硬件）。
- 需要听、看、量、闻。
- `git add/commit/push`、发 issue/PR、回维护者、对外发布。
- 改开发机/编译机环境（装包、sudo、服务、网络、公钥）。
- 改计划范围（新阶段、新板子、新系统）。
- **改已定稿的计划**（即使只是措辞），必须先得到人明确同意。
- 改设备网络（**逐次授权**，不是永久禁止）。
- 结论要从"推断"升级为"已解决"之前。

## 4 回合接口

agent 给"命令块 + 判读表"，人执行并回传全文，agent 判读后产出下一版。

```
请执行（复制即可）：

    sudo rkdeveloptool list

看到什么就回什么：
- 出现 "Maskrom" → 我们继续下一步；
- 出现 "No devices found" → 换 USB 口/换线，再试一次；
- 报权限错误 → 需要 sudo，或 udev 规则没装。
```

要点：

- 命令块要能直接复制，不要夹注释。
- 判读表覆盖"成功/失败/意外"三种。
- 明确"回传什么"：全文、截图、还是只回一行关键值。
- **独占资源要显式交接**：串口同一时刻只能一个程序持有；人关掉串口助手，agent 才能用。

## 5 汇报模板

```
结论：<一句话>
证据：<命令> → <关键输出 ≤10 行>；落盘：<路径>
下一步：我做 <X>；需要你做 <Y>（一条命令/一个动作）
风险/未验证：<列出来>
```

用户要的是"现在能不能继续"，不是过程传记。**细节放日志，回复只留结论与动作。**

## 6 交接

一个会话结束时，留下三样东西，让下一个会话能接上：

1. **进度页**：现在在哪、哪些阶段完成、下一步是什么。
2. **最后一份日志**：这次做了什么、结论、遗留。
3. **board-profile**：事实有没有更新。

新会话开场只需要读这三样，不要重新规划。

## 7 不同用户类型

| 类型 | 特征 | 怎么配合 |
|---|---|---|
| **动手型玩家**（最常见） | 会接线、会测量、能刷机；软件原理弱 | 多给"手怎么放"的动作；DTS 原理讲到够用即可；不要用术语堆砌 |
| **软件工程师** | 会读代码、懂 Linux；硬件生疏 | 多解释电平/时序/焊接；不要假设他知道 MaskROM |
| **有经验的移植者** | 两边都懂 | 直接给结论与证据，少铺垫；他会自己纠偏 |

判断方法：问一个具体问题（"串口 TX 空闲电压是多少"），看回答的速度和准确度。

## 8 无人值守 / 夜间托管

可以，但有边界：

- 允许：写文件、编译、离线分析、只读诊断、准备材料。
- 不允许：需要断电/刷机/按键的动作——排队等人回来。
- 收尾：写一份"早上回来先做什么"的清单，标清哪些在等他。

## 9 红线

- 不代替人执行破坏性操作。
- 不猜硬件；不从 dts 片段反推接线。
- 不写用户的笔记/学习记录目录，也不主动准备"待粘贴片段"。
- 不代为 git 写操作与对外发言。
- 不把计划写成已完成。
- 不扩大范围。

## 10 一句话

**人当 PI + 实验员，agent 当研究员 + 工程师 + 记录员。**
方向、取舍、签字在人；证据、执行、归档在 agent。两边都不越界，这套流程才跑得动。
