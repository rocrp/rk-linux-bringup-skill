# 13 工作目录与文档规则（强制）

> 这一篇不是风格偏好，是**强制规则**。
> 没有独立目录和四件套，agent 会串板、会重复规划、会在下一个会话里失忆；
> 用户也没法一眼看出"现在到哪了"。

## 1 一块板 = 一个独立目录

- **禁止多块板共用一个工作目录**。共用目录会让 board-profile、日志、镜像混在一起，
  下一个会话分不清"这条结论是哪块板的"。
- 目录名用 `<board>-bringup`（小写、连字符、不含日期和版本），例如 `rk356x-demo-bringup`。
- 板子做完或放弃后，整个目录**归档**（`archive/<board>-<YYYYMMDD>/`），不要清空复用。
- 不要把其他项目、其他板子的文件放进这个目录。

## 2 固定目录结构

```
<board>-bringup/
├── AGENTS.md              # 本项目的 agent 规则（从 templates/project-AGENTS.md 复制）
├── board-profile.md       # 板卡档案：唯一事实源（必须）
├── feasibility.md         # 可行性分析（必须，P0 产出）
├── plan.md                # 实施计划（必须，定稿后冻结）
├── progress.md            # 进度页（必须，只写状态 + 日志索引）
├── logs/                  # 会话日志（必须）
│   ├── session-01-P0.md
│   ├── session-02-P1.md
│   └── ...
├── dts/                   # 工作副本：<board>_v1.dts …（只增不改）
├── evidence/              # 取证：dtb、dmesg、分区表、照片（按日期）
├── images/                # 镜像、备份、payload（大文件，不入库）
└── release/               # 对外发布包（可选）
```

**四个文件必须在顶层、用固定文件名**——不要藏进子目录，也不要改名。
目的很简单：人和 agent 打开目录就能看到"这块板是什么、打算怎么做、做到哪、做过什么"。

## 3 四件套（缺一不可）

| 文件 | 回答什么 | 谁写 | 何时写 | 规则 |
|---|---|---|---|---|
| `board-profile.md` | 这块板的事实 | agent 起草，人确认 | P1 开始，随事实更新 | 每项带"证据级别 + 出处 + 状态" |
| `feasibility.md` | 能不能做、做到哪 | agent | P0 | 一次成型；结论明确 go / 条件 go / no-go |
| `plan.md` | 该做什么、怎么验、失败怎么退 | agent 起草 | P0 | **人确认后定稿并冻结**；之后改动需人批准 |
| `progress.md` | 现在到哪了 | agent | 每次会话收尾 | 只写状态与日志索引，**不写细节** |
| `logs/session-NN-*.md` | 实际做了什么 | agent | 每个对话一份 | 细节只写这里；已结束的只增不改 |

> `board-profile.md` 是第五件，但它是"事实源"而不是"过程文档"，单独列在最上面。

## 4 文档规则

### 4.1 计划：一次成型，确认后冻结

1. agent 先出**草案**，明确标"草案，待确认"。
2. 人看完说"可以/定稿/按这个来"，才算定稿；**没有这句确认，不许开工**。
3. 定稿后：
   - 只有**人提出**或**人批准**的计划变更才能改（范围、阶段、门槛、路线、依赖）；
   - 每次改动在 `plan.md` 末尾的「修订记录」加一行：日期 / 改了什么 / 为什么；
   - 日常进展、临时发现、失败尝试**不许写进计划**，写到会话日志。
4. 计划里不写"已完成"的细节；状态用 `⬜ / 🟡 / ✅ / ➖` 标在条目上即可。

### 4.2 进度：只写"在哪"，细节指向日志

- 「当前位置」**一句话**，不超过 100 字，只说明处于哪个阶段（可带一个已完成的小阶段号）。
- 「阶段完成度」按小阶段逐行，只标状态，不写命令、数字、路径、引脚、现象。
- 「会话索引」一行一份日志：会话号 / 阶段 / 日期 / 主题 / 一句话结论。
- 已解决的条目直接删掉，不留"已修复"的历史。
- **判据**：人扫一眼能知道现在能不能继续、下一步是什么；想知道为什么，点进日志。

### 4.3 会话日志：一个对话一份，细节都在这里

- 一个**对话线程**一份，不是一轮、不是一天、不是一个阶段。
- 文件命名 `session-<NN>-<phase>.md`，序号补零（`01`、`02`…），保证排序正确。
- 内容：设备状态、目标、动作表（命令/结果/证据）、结论分级、遗留、原始片段。
- 会话未结束可以边写边改；**已结束的只增不改**，发现错误就在新日志里写"更正 session-XX"。
- 命令必须真跑过；没跑的写"未执行"，没验证的写"未验证"。

### 4.4 板卡档案：每条事实都要能追

- 一行一个事实：值 / 证据级别（L1~L5）/ 出处 / 状态。
- 拿不到的值写"未确认"，不要留空、不要猜。
- 事实变化时直接改，但在「变更记录」里留一行。

## 5 开工检查（agent 必须执行）

进入 P0 实操之前，逐条确认：

- [ ] 工作目录是**这块板专用**的，里面没有别的板子的文件？
- [ ] `board-profile.md`、`feasibility.md`、`plan.md`、`progress.md`、`logs/` 都在？
- [ ] `plan.md` 有人的确认记录（不是"草案"状态）？
- [ ] `AGENTS.md` 已从模板复制并按本项目改过？

任何一项为否：**先建目录、补文档、等确认**，再进 P0。
用户明确说"先随便试试、不做文档"时，可以只保留 `board-profile.md` + `logs/`，
但要在第一次日志里记下"本次为探索性会话，未建完整四件套"，并在正式开工前补齐。

## 6 反模式

| 反模式 | 后果 |
|---|---|
| 多块板共用一个目录 | 档案/日志/镜像串味，下一个会话分不清 |
| 计划边做边改、不留痕 | 计划退化成流水账，既不能当清单也不能当档案 |
| 进度页写成第二份日志 | 查进度要读长文，人不再看它 |
| 日志按天/按轮拆 | 一个对话散成多份，无法回溯 |
| 把镜像/备份塞进版本库 | 仓库膨胀，diff 失去意义 |
| 文档藏在子目录、随意改名 | 人和 agent 都找不到 |
