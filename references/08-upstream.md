# 08 上游化

> 目标：把"我这块板能跑"变成"别人也能用"，并且不浪费维护者的时间。
> 这一步是可选的，但它是这套方法里唯一能留下公共价值的部分。

## 1 先问规则，再动手

不同仓库的偏好不同，提交前先确认：

- 拆成几个仓库/几个 PR？
- commit 风格（单行？带 `Signed-off-by`？）
- 产物要求（dtb 要不要带 `__symbols__`？镜像要不要附？）
- 证据要求（维护者通常先要"你测过"的日志，再谈代码）。

**先提 issue 探路，再拆 PR**，比直接甩三个 PR 更省事。

## 2 dts 整理成主线风格

| 要求 | 做法 |
|---|---|
| 用 `#include "rk3xxx.dtsi"` + 板级覆盖 | 不要提交几千行展开版 |
| 只留 SPDX + 几行板级说明 | 删调试注释，但保留"为什么这么写"的关键一两行 |
| `model` / `compatible` 用正式名称 | 对外名称与丝印不一致时，以对外名称为准，丝印在说明里提一句 |
| 用上游当天 HEAD 的头文件编译 | 避免"我这能编、你那一堆 warning" |
| dtb 带 `__symbols__` | 否则 overlay 失效 |

可以用脚本做"删注释 + 换名"，但必须**断言输出代码流与源文件一致**（只删注释不应改变 dtb），
并断言"没有残留旧板名"。

## 3 issue 写什么

一份好的适配 issue：

1. **设备信息**：整机名、主板丝印、SoC、内存/存储、主要外设型号、原厂系统版本。
2. **做了什么**：用了哪个底料镜像、内核版本、dts 放在哪、dtb 怎么来的。
3. **验证矩阵**：外设逐项 ✅/🟡/➖，每项一句"怎么验的"。
4. **已知限制**：哪些不做、为什么；哪些"能跑但不保证"。
5. **材料**：dts、dtb、测试镜像（说明"仅供验证，不是交付物"）、日志。
6. **复现步骤**：别人怎么把你这版跑起来。

写作口径：**只写站得住的部分**；未验证的明确标"未验证"，不要用"应该"。

## 4 三个 PR 的分工

RK 平台的适配通常拆成三个仓库：

| 仓库 | 提交什么 | 注意 |
|---|---|---|
| **内核仓** | `arch/arm64/boot/dts/rockchip/<soc>-<board>.dts` + `Makefile` 一行（+ 需要时 `vendor-prefixes.yaml`） | 主线风格；编译通过；最好附 dtb 大小/符号数 |
| **引导仓** | `u-boot/rockchip/<board>/` 下的引导文件 | 多数情况**不用新编**：从板子读回，与某个已知可用型号逐字节相同即可复用；不同才需要自建 |
| **发行版仓** | `model_database.conf` 一行 + 预编 dtb + 相关 workflow/README | 编号（r 号）**当天重核**，不要抄旧的；dtb 必须带 `__symbols__` |

> 引导仓很多是"预编译 blob 仓"，不是源码仓。提交前确认它收什么形态。

## 5 提交前必做

1. **用最终要提交的那份源码产物做一次真机回归。**
   常见错误：真机跑的是反编译整理版，提交的是源码重写版，两者不是同一份产物。
2. **控制组复现**：用上游已合并的同族 dts 编一次，确认你的工具链/头文件没有引入无关差异。
3. 分支 `ahead 1 / behind 0`；文件清单逐项核对。
4. commit 风格跟仓库；不要夹带无关改动。
5. 日志脱敏：IP、MAC、序列号、口令、主机名。
6. issue ↔ PR 互链；PR ↔ PR 互链。

## 6 与维护者沟通

- **先给证据，再给代码**。维护者要的是"你测过"，不是"我觉得行"。
- **主动解释看起来奇怪的写法**（例如为什么用 `gpio-hog` 而不是 `regulator-fixed`），
  并说明"这是实测结论，不是偷懒"。
- **不扩大范围**：回复只补链接、sha256、按需日志；不承诺未验证的功能。
- **已知限制要写条件**："此结论仅在某镜像/某显示器组合下成立"。
- 被要求补证据 → 回去补回归，不要用"我测过"代替。
- 合并后用官方产物再冷启动一次（有条件的话）。

## 7 release 包

对外发布物建议这样组织：

```
release/<board>/
├── README.md            设备信息、验证矩阵、已知限制、刷写步骤
├── dts/                 提交版 dts + dtb
├── patches/             三仓补丁（0001/0002/0003）
├── logs/                脱敏后的验证日志（按外设分文件）
├── photos/              板卡照片（如需要）
├── ISSUE_DRAFT.md       issue 正文
└── SHA256SUMS.txt
```

规则：

- 日志必须脱敏；
- 镜像如果太大，给网盘链接 + sha256，不入库；
- 明确标注"测试镜像不是交付物"；
- `SHA256SUMS.txt` 覆盖所有文件。

## 8 反模式

- 没提 issue 就直接甩三个 PR。
- 抄旧的 `model_database` 编号，导致冲突。
- 提交版 dts 里还留着调试注释和旧板名。
- 用"我测过"代替日志。
- 把未验证的外设写进"已验证"表。
