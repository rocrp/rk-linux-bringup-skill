# rk-linux-bringup-skill

**一个面向 Rockchip（RK3399 / RK356x / RK3588）板卡的 Linux 适配 skill：
让 AI agent 和你一起，把一块只有原厂系统的旧板子，按阶段适配到 Armbian / 主线 Linux。**

[English](README.en.md) · [更新日志](CHANGELOG.md) · [贡献指南](CONTRIBUTING.md) · MIT

---

## 背景

**嵌入式 DIY 的乐趣**，是用很低的成本把淘汰的硬件救活：刷脸机、广告机、电视盒子、云电脑主板……
几十到几百块钱一块，硬件规格却常常比同价位的开发板好得多。经典玩法是电视盒子、软路由、NAS、轻量服务器。

软件/系统这边已经有了成熟的开源生态：**Armbian** 提供通用的 ARM 发行版与镜像框架，**OpenWrt** 负责路由，
**飞牛 OS** 这类国产 NAS 系统也在补齐。这些开源专用Linux发行版构建起了庞大的DIY社区。

然而，从每个人手里的电路板，到能用起来这些开源系统，中间还有一层：

> **每块板子的厂商都不一样，设计不公开，原厂只给一个 Android 或闭源 Linux。
> 想跑通用 Linux，就得自己把设备树（dtb）适配出来。**

并不是每一位DIY爱好者都有足够的技术储备，来解决这个过程中遇到的复杂问题：
反编译 DTB、写 DTS、看启动日志、打包镜像，以及有耐心一遍遍刷机试错。

很多玩家，都因为这样的门槛，只能寄希望于其他的大佬刚好适配手里的这块板子。很多期待往往受阻于此……
**……直到AI agent出现。** 

AI agent，我们这个时代最强的开发者、最强的架构师、最专业的专家、最博学的词典。

它擅长读海量日志、反编译二进制、比对设备树、查内核 binding、写脚本和文档——恰好是适配里最耗时的部分。
而人，仍然掌握着 agent 没有的东西：手、眼、万用表，以及对"这块板子值不值得救"的判断。

**本仓库要做的**，就是把这种"人机合作"写成一套可复用的规程：**一个 agent skill**
加上通用工具、文档模板和协作协议，希望通过这个仓库，真正把玩板子的技术门槛降下来，打开更多的可能。

## 为什么是瑞芯微(RockChip)？

到目前为止，使用RK系列芯片的板卡厂家几乎不会加锁。这就使得这类板子回收再利用价值很大。
另一方面，RK的MASKROM模式使得哪怕uboot刷坏了也能救。

这就意味着，RK板子是“几乎不用担心刷成砖”的板子，除非eMMC本体损坏。

[ophub仓库](https://github.com/ophub/amlogic-s9xxx-armbian)支持RochChip(瑞芯微)/Amlogic(晶晨)/Allwinner(全志)三家，我目前只熟悉RK.

因此，本仓库支持RK芯片的适配。其他厂家或许之后会支持，或许不会。

## 它解决什么问题

市面上的 RK 适配资料，大多是"某块板子的结论"：一份 dts、一篇 issue、一个镜像。
换一块板子，这些结论几乎都用不上。

这里提供的是**过程**：

- 拿到一块完全陌生的板子，第一步该问什么、该测什么；
- 怎么从原厂系统里把设备树、分区表、引脚信息挖出来；
- 怎么在不写 eMMC 的前提下，让主线内核先跑起来；
- 怎么一个外设一个外设地点亮，每步都有可验证的判据；
- 怎么把成果装进镜像、冷启动验证，最后整理成能提交上游的 dts。

它不替你适配，但它让 agent 知道**下一步该做什么、什么算做完、什么时候该停下来问你**。

## 适用条件

| 条件 | 说明 |
|---|---|
| **RK 芯片** | RK3399 / RK356x / RK3588 等，主线内核有 SoC 支持 |
| **板子完好** | 能上电、能进原厂系统（至少能进 MaskROM） |
| **原厂系统还在** | 适配的第一步是从它里面取证；刷掉了会很麻烦 |
| **有 TTL 串口** | 已引出或能焊出来；这是唯一的"眼睛" |
| **知道 MaskROM** | 按键位置 + 对应 USB 口，是救砖通路 |
| **能备份** | 有备份盘、能读 flash、能刷回去 |

缺串口或缺备份，不建议开工——后面每一步都会变成盲改。

## 使用方法

### 1. 装 agent

Claude Code、Codex、Cursor、Gemini CLI、DeepSeek Harness 等都可以。本 skill 只依赖
"能读写文件、能跑命令"这类基础能力。

### 2. 装 skill

跨工具通用位置是 `~/.agents/skills/`：

```bash
git clone https://github.com/weixr18/rk-linux-bringup-skill.git \
  ~/.agents/skills/rk-linux-bringup-skill
```

其他位置（任选其一）：

| 工具 | 位置 |
|---|---|
| Claude Code | `~/.claude/skills/rk-linux-bringup-skill/` 或项目内 `.claude/skills/` |
| DeepSeek Harness | `~/.dsh/skills/`、`~/.agents/skills/` 或项目内 `.dsh/skills/` |
| 项目内共享 | `<项目>/.agents/skills/rk-linux-bringup-skill/` |

装好后，agent 的技能列表里应该出现 `rk-linux-bringup-skill`。

### 3. 完成四组接线

| 接线 | 作用 |
|---|---|
| **USB** | 刷机 / MaskROM（部分板子同时供电） |
| **串口** | 启动日志与登录 shell，注意电平（TTL 还是 RS-232） |
| **网口** | 与开发机同网段，用于 SSH、TFTP |
| **HDMI** | 第二条"眼睛"，看画面（建议配 USB 采集卡） |

### 4. 开始交互式适配

在一个新目录里打开 agent，说一句：

> 我要给这块 RK 板子适配 Linux，板子型号是……，原厂系统是……，串口在 COMx。

然后按它的问诊回答。它会先让你补事实、确认退路，再进入 P0。

**建议节奏**：一个会话推进一个小阶段，结束前让它写日志、更新进度页。
下一个会话开场只需要给它三样东西：实施计划、进度页、上一份日志。

## 工作流总览

```
P0 立项 ──► P1 取证 ──► P2 观测 ──► P3 点亮 ──► P4 外设 ──► P5 固化 ──► P6 上游
   │           │           │           │           │           │
   └─ 退路     └─ 事实     └─ 眼睛     └─ 内核     └─ dtb      └─ 镜像
      G0          G1          G2          G3          G4          G5        G6
```

| 阶段 | 一句话 | 门槛 |
|---|---|---|
| **P0 立项** | 决定做不做、做到哪 | 能回刷、能救砖、范围写死 |
| **P1 取证** | 把未知变已知 | 关键事实都有出处，备份可校验 |
| **P2 观测** | 造两条独立的眼睛 | 能从 DDR 第一行抓到 `login:` |
| **P3 点亮** | 零写入介质上跑起主线内核 | 串口 + 电源 + 存储 + 网口 probe |
| **P4 外设** | 一次一类，按依赖链 | 核心集全通，dts 冻结 |
| **P5 固化** | 可复现、可交付 | 断电冷启动 3/3 |
| **P6 上游** | 让别人也能用（可选） | PR 合并或明确不收 |

真正花时间的不是写 DTS，而是**取证、观测、固化**。写 DTS 往往只占整个工期的五分之一。

## 工作目录与文档

**一块板一个独立目录**，不要多块板共用一个。目录里固定放四样东西：

```
<board>-bringup/
├── board-profile.md    # 事实源：这颗芯片/这个引脚从哪看到的
├── feasibility.md      # 能不能做、做到哪、明确不做什么
├── plan.md             # 该做什么：阶段、门槛、失败怎么退
├── progress.md         # 现在到哪了：一句话 + 每小阶段一行 + 日志索引
└── logs/
    └── session-01-P0.md  # 实际做了什么：命令、结果、证据、遗留
```

规则很简单，但很重要：

| 文档 | 规则 |
|---|---|
| **可行性** | P0 一次成型，结论明确 go / 条件 go / no-go |
| **计划** | 先出草案，你确认后定稿并**冻结**；之后改动必须你提出或批准，并留修订记录 |
| **进度** | 只写"在哪"和每小阶段状态，**不写细节**；想深究就点进会话日志 |
| **会话日志** | 一个对话一份，序号补零；细节只写这里；已结束的只增不改 |

这样做的好处：换一个 agent、换一天、换一个人接手，打开目录就知道
"这块板是什么、打算怎么做、做到哪、做过什么"，不用翻聊天记录。

目录骨架、命名与开工检查清单见 [`templates/workspace-layout.md`](templates/workspace-layout.md)，
完整规则见 [`references/13-workspace.md`](references/13-workspace.md)。

## 技术原理

**dtb 是什么？** ARM 世界没有 x86 的 ACPI/PCI 自动枚举。板子上有哪些外设、接在哪个引脚、
用哪个时钟、由哪路电源供电，全靠一份叫 **device tree blob（dtb）** 的二进制描述，
内核读它来发现硬件、绑定驱动。

**为什么麻烦？** 每块电路板的走线都不同，所以 dtb 天然不通用。原厂只给编译好的 dtb，
不给源码；而主线内核需要的是另一份、按自己 binding 写的 dtb。

**dts 与 dtc**：dts 是文本源码，dtc 负责编译成 dtb，也能把 dtb 反编译回 dts。
适配的日常工作，就是读懂厂端 dtb、写自己的 dts、编译、投放、验证。

**一句话概括**：

> 通过串口从原厂系统尽量提取信息，由 AI 生成各外设的 dts 节点，分步验证可用性，
> 最后集成打包成可用镜像刷入，并可分享给开源社区。

## 常见问题

**没有串口怎么办？**
找测试点、焊排针，或者换一块板。串口是唯一能看到启动过程的地方，没有它只能靠猜。

**板子没有 TF 卡槽？**
可以走 TFTP 内存直启或 USB rootfs，全程不写 eMMC。见 `references/04-boot.md`。

**原厂系统已经刷掉了 / 没备份？**
先尝试救砖（MaskROM + 厂端固件）。救不回来就只能按 SoC 公版设计从头推，难度高很多。

**一定要用 Armbian 吗？**
方法是发行版无关的；镜像装配那一章以 Armbian 为例，因为它的 `fdtfile` 机制最省事。

**会变砖吗？**
有备份和 MaskROM 通路，通常能救回来；但没有百分之百的保证。第一次写 eMMC 前，务必确认备份可读。

**需要什么水平？**
会接线、会看串口输出、会用万用表就够了。DTS 怎么写，agent 会带你一步步来。

**支持 32 位 ARM 吗？**
本 skill 面向 arm64 的 RK3399/RK356x/RK3588。32 位平台思路相同，但镜像与工具链要另配。

## 限制与免责

- **不写新驱动**：主线没有的驱动，写进"不做清单"，不在适配现场开发。
- **不自建 U-Boot/内核**：只提供入口说明（`references/12-branch-c.md`），不含操作手册。
- **不保证成功**：硬件批次、原厂固件、主线支持度都会影响结果。
- **可能损坏硬件**：电源使能、GPIO 极性写错会真的烧板子。涉及电源的改动必须人肉复核。
- **不替代专业维修**：焊接、拆焊、BGA 返修请找专业的人。
